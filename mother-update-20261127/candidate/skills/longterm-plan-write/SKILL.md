# 급여제공계획서 작성

추가 확인 질문은 [공통 확인 질문](../sequential-clarification/SKILL.md)을 따른다. 전체 질문 목록을 먼저 안내하고 한 번에 하나씩 답을 받는다.

서술형 업무 문장은 확인된 사실을 구체적인 업무 기록체로 쓴다. 본문에서 특정 날짜와 출처 설명을 생략하고 근거와 필수 날짜 입력란에 보존한다.

[설치본 실행 안내](../../assets/runtime-guide.md)를 따른다. CM기초평가·계약·이용계획서와 같은 기관LT대상을 확인한다. 원천·초안·명세·실행/완료 이력은 기관별 개인 폴더에 둔다.

대상과 전체 작성 범위가 명확한 요청은 그 범위의 작성 지시다. 검토/개발 요청을 실제 저장으로 확대하지 않으며 같은 요청의 승인을 반복해서 받지 않는다. 필요한 사실/선택이 빠진 경우만 확인한다. 문서 검토 후 저장·입력만·특정 부분 수정 등 사용자가 지정한 경계를 우선한다.

## 자료와 초안

1. 현재 대상의 욕구사정·낙상/욕창/인지 기록, 계약·인정/이용계획서의 식별자·기간·현재 작성자를 확인한다. 미래 평가를 현재 사실로 쓰지 않는다. 필요내용은 확인된 욕구/기능에 근거하며 이용계획서는 횟수·시간·상이한 부분 비교에 사용한다.
   기관별 업무폴더의 preferences.json에 실제 사용자 발언과 함께 저장된 상시 작성 기준이 있으면 재질문하지 않고 반영한다. 동의자 이름은 현재 수급자로 치환하고 동의일은 명시된 기준으로 산정한다. 이번 건에만 지정한 최종확인자를 상시 기본값으로 확대하지 않는다.
2. `plan-draft.ps1`은 ContentFile 없이 먼저 원천/명세를 수집한다. `source-collected-needs-draft-content`는 초안/저장 완료가 아니다.
3. Codex가 원천을 읽어 [내용 작성 규칙](references/rules.md)에 맞는 근거 연결 내용 파일을 만든다. 이전 기관의 고정 문구·부축 기본값·방문 횟수·180/240분·동의일·본인동의·계획서 순번을 자동 복사하지 않는다. 현재 기관의 채택 기준과 해당 대상의 실제 자료/사용자 지시로 정한다.
4. 같은 source/evidence를 `DumpFile`/`ManifestFile`로 재사용하고 ContentFile을 넣어 새 폴더에 DOCX를 만든다. `info.inputReady=false`이면 입력용spec은 생성되지 않는다. Word 전 페이지를 렌더링해 확인한다.

실행 명령·파일과 근거 연결 구조는 [재사용/실행 절차](references/efficiency-workflow.md), PDF 선택/판독은 [이용계획서](references/util-plan.md)를 읽는다.

신규 계약의 최초 작성은 최초급여계약을 선택한다. 재작성은 롱텀 화면의 작성사유 목록에서 사용자 선택을 받아 `plan-draft.ps1 -Reason '<선택한 표시 문구>'`에 반영한다. 이미 받은 선택은 재사용한다. 새 계획서 등록은 신규 계약과 다르다. 적용 시작일은 신규 최초 제공이면 실제 계약·제공 시작일(작성일과 같을 수 있음), 기존 계획에 이어 작성하면 이전 계획 종료일 다음 날, 인정 갱신이면 갱신 인정 시작일로 정한다. `-WriteDate`는 실제 작성일, `-From`은 이 기준으로 확인한 시작일을 각각 넣는다. `periodBasis`에 initial/continuation/renewal 구분과 실제 계약·인정기간, 연속 작성이면 이전 계획 번호·종료일을 근거와 함께 남긴다. 기존 계획과 중복·공백 및 계약·인정기간을 대조하며 작성일과 적용일을 억지로 일치시키지 않는다.

계약 종료일·급여이용계획 횟수/시간·이용계획서 번호·현재 평가가 확인되지 않으면 unresolved로 남기고 입력하지 않는다. 확인한 계약 방문시간과 종합의견 제공시간이 등급 기본 180/240분보다 우선한다. 두 시간과 일 단위 항목 합계가 정확히 같은 값이어야 하며 범위·대략 표기는 확인 전 확정하지 않는다. 양치 10분을 임의로 필요시로 낮추지 않는다. 상세는 규칙 20과 생성기 검증을 따른다.

## 실제 저장

현재LT기관·인정번호/순번·계약/인정기간·같은 기간 중복·통보 여부·미저장 화면을 대조한다. 생성기 통과는 임상 내용의 승인이나 현재 서버 상태의 증명이 아니다. 누락/decisionNeeded·다른 대상·중복·이미 통보됨·unknown은 해당 상태를 먼저 해결한다.

재작성 요청으로 새 계획을 만드는 경우에는 기존 계획이 적용 중이거나 통보됐어도 확인된 자료로 새 초안을 작성한다. 기존 계획은 보존하고 새 계획의 중복·통보 상태를 별도로 확인한다.

사용자가 기존본을 보존하고 새로 작성하라고 지시하면 같은 적용기간이라는 이유만으로 새 등록을 금지하지 않는다. `creationIntent`에 type=additional, 사용자 지시 원문, 요청 시각·고유 requestId와 현재 겹치는 기존 계획서 번호 전체(preservePlanNos)를 넣고 같은 사용자 근거를 evidence.creationIntent에 연결해 새 명세를 생성한다. 한 작성 지시의 requestId는 재사용하고 재시도 때 바꾸지 않는다. 등록 직전 보존 대상 목록이 달라지면 중단한다. 기존 명세의 성공/unknown 원장은 보존하고 같은 요청의 성공을 새 명세 해시로 다시 등록하지 않는다. 등록 후 새로운 계획서 번호 1개와 기존 번호 보존을 대조하며 이후 쓰기는 새 번호로만 진행한다. 기존 기간·계약/인정범위·미통보 확인을 생략하지 않는다.

`lt-plan-run.ps1`은 승인된 전체 작성의 register→select→writer→needs→cycle→final→독립 재조회/검증→park를 연결한다. 기존 미통보본의 부분 수정은 명확한 요청 범위에서만 등록을 생략하고 해당 단계만 사용한다. 필요내용 해제는 별도 지시와 개별 needs의 AllowRemove로만 한다. 기존본을 임의 삭제하지 않는다.

Apply에는 실제 지시 범위와 명세 해시·현재 InstitutionId가 필요하다. 해시는 추가 승인 문장이 아니며 같은 범위에 다시 묻지 않는다. 단계별 CreateNew 시도 이력과 서버 점유/재조회 보호를 유지한다. 저장 불명은 다시 저장하지 않고 서버 내용부터 대조한다.

최종에는 대상/계획·기간·모든 선택/주기/목표/서술·동의/전화/작성자/확인자·미통보를 [검증 절차](references/efficiency-workflow.md)대로 비교하고 팝업 없는 계획 통보서 탭에 둔다. [화면 구조](references/lt-screen.md)는 진단할 때만 읽는다. 통보·삭제·인쇄 클릭은 포함하지 않는다.
