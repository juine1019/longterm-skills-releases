# 업무데스크 결과평가 6-1·6-2

## 6-1 초안 작성과 게시

1. 사용자가 지정한 수급자를 찾는다. 종사자 20L 로그인에서 **급여기록관리 → 급여제공결과평가 → 수급자명 → 조회 → 입력** 순으로 이동한다. 계획서 목록에서 일치하는 계획서 행을 더블클릭한다. 조회 결과와 현재 검색 조건이 일치하는지 먼저 확인한다. 동명이인이나 유효한 계획이 여럿이면 대상 또는 계획을 확정한 뒤 진행한다.
2. 화면에 표시된 대상·인정번호와 순번·계획서 번호·서비스기간을 대조한다. 작성자는 현재 로그인한 종사자 이름이며 직종은 화면에서 확인한다. 대상이나 작성자 이름을 이전 실행에서 가져오지 않는다.
3. 20L 가정방문형 일지와 같은 기관 20A 요양요원 전송내역 상세를 계획 시작일부터 평가일까지 읽는다. 작성 내용이 있는 일지는 서명 대기여도 포함한다. 미작성 표시(X)만 있는 조회는 작성된 일지 0건으로 기록한다. 조회 실패와 작성된 일지 0건을 구분한다. 계획이나 태그만으로 제공을 단정하지 않는다.
4. 계획별 제공 확인, 총평, 심신상태별 판단근거와 기타 및 종합의견, 욕구 및 향후계획을 실제 근거에 연결한다. 총평과 기타 및 종합의견은 구체적인 업무 기록체로 쓴다. 본문에 날짜·출처 설명을 반복하지 않고 근거 목록에 보존한다. 확인할 수 없는 달성률·변화·미제공 사유는 추정하지 않는다.
5. 형식과 근거 연결을 검증한 초안을 운영 업무데스크에 게시하고 독립 조회로 확인한다. 대상이 지정된 6-1 요청에는 초안 게시까지 포함한다. 같은 내용이면 기존 건을 알리고 다른 내용이면 새 회차 후보로 게시한다. 사용자가 업무데스크에서 직접 검토완료를 누른다.

게시 요청을 보낸 뒤 응답이나 독립 조회 확인을 잃으면 결과는 미확인이다. 같은 지시·검토폴더·점유 ID로 `evaluation-desk-publish-check`를 실행한다. 업무데스크에서 해당 평가의 현재 내용과 **같은 기관·요청자·평가·요청 ID의 처리 증거**를 모두 읽어 확인한다. 전송 전 중단이 로컬 기록으로 확인된 경우에만 `not-written`으로 정리한다. 목록이 비었거나 같은 내용이라도 요청 증거가 없으면 점유를 유지한다. 내용이 바뀌면 충돌로 남긴다. 복구는 조회만 하며, 다시 게시하거나 초안을 삭제하지 않는다.

요청 처리 증거는 제품의 호환 API가 제공한다. 이전 제품이나 전송 사전 기록이 없는 이전 실행에서는 증거를 추정하지 않는다. 문제를 진단할 때 해당 실행 기록과 점유를 보존한다.

여러 대상의 6-1 게시를 한 번에 지시하면 `evaluation-desk-publish-sequence`로 순서대로 게시한다. 규칙은 아래 「여러 대상 6-2 순차 처리」와 같다. 한 대상의 게시가 미확인이어도 나머지를 계속 게시하고, 미확인 대상은 `evaluation-desk-publish-check`에 순차 실행 결과의 `leaseId`를 넘겨 정리한다. 근거 수집과 초안 작성은 대상마다 먼저 끝낸다.

특이사항 보관소(2026-11-17): 작업공간 특이사항 보관소(`runtime/worker-notes-store.cjs`, 기관 상태 폴더의 `worker-notes/`)에 **확정월** 스냅샷이 있으면 그 달은 RFID 목록·상세를 다시 읽지 않고 같은 원문을 쓴다(커버리지에 `storedSnapshot` 해시·원래 수집시각). 당월·미확정·필드 누락·실패 이력만 있는 달은 위 경로로 실제로 읽는다. 보관 원문의 차수·기관이 다르면 빈 달이 아니라 실패로 남긴다. 6-2는 검토완료본을 그대로 쓰며 재수집하지 않는다.

6-1에서 정확한 대상의 롱텀 평가 화면에 있는 성별·생년월일·장기요양등급을 읽어 평가 묶음과 업무데스크 기본정보에 보존한다. 만 나이는 평가일을 기준으로 계산한다. 원천 값이 없거나 확인되지 않으면 빈칸으로 둔다. 기존에 게시한 평가의 기본정보는 별도로 확인되기 전까지 추정하지 않는다.

## 6-2 롱텀 반영과 확인

1. 검토완료는 해당 버전의 입력·저장 승인이다. 검토완료본의 문장과 선택을 그대로 옮기고 원천 사이트 기록을 다시 수집하거나 동일 승인·검토를 반복하지 않는다. 여러 검토완료본 중 요청으로 특정할 수 없으면 대상·기간·평가일·차수를 보여 주고 선택받는다. 초안과 등록완료는 신규 등록 후보에서 제외한다.
2. 로그인한 20L 종사자, 정확한 계획과 서식, 검토완료본의 평가일을 확인한다. 새 화면 기본 날짜 대신 검토완료본의 날짜를 사용한다. 같은 계획의 저장 목록으로 다음 차수를 정한다. 같은 계획·기간·평가일의 중복, 차수 불일치 또는 미확인 저장이 있으면 해당 건을 보류한다. 다른 날짜의 동일 계획은 다음 차수로 처리할 수 있다.
3. 최신 버전과 해시를 대조하고 등록 점유를 얻는다. 현재 화면을 채운 뒤 읽어 맞는지 확인하고 롱텀의 정상 저장 버튼을 한 번 누른다. 서버 재조회와 저장된 평가 재열기로 날짜·차수·내용을 대조한 뒤 업무데스크에 등록완료를 기록한다. 두 곳의 완료 상태를 확인한다.
4. 저장 또는 응답 여부가 불명확하면 재클릭하지 않는다. 해당 실행의 기록과 저장 목록을 대조하여 복구한다. 롱텀에서 저장을 확인했고 업무데스크 결과만 누락된 경우에는 결과 보고만 복구한다.

### 여러 대상 6-2 순차 처리(2026-11-15)

사용자가 여러 대상의 6-2를 한 번에 지시하면 대상마다 위 1~4를 그대로 하되 한 대상의 문제로 나머지를 멈추지 않는다.

- 대상마다 기존 등록 준비(`evaluation-desk-register-prepare`)와 단건 등록 지시를 만든다. 작업 목록은 처리 순서일 뿐 저장 승인이 아니며, 각 대상의 검토완료본 바인딩·해시·평가일 검사를 생략하지 않는다.
- 순차 실행이 공용 점유를 한 번 잡고 끝까지 유지한다. 각 대상은 자기 실행 기록 잠금만 잡는다. 실행 중 다른 실행기는 진입할 수 없다.
- 대상 결과는 처리됨(롱텀 저장·재조회·재열기·업무데스크 등록완료 확인), 미처리(저장 전 차단), 미확인(저장·응답·보고 불명)으로 나눈다. 미확인 대상은 실행 기록 잠금과 증빙을 그대로 두고 다음 대상으로 넘어간다. 다시 입력하거나 삭제하거나 완료로 바꾸지 않는다.
- 로그인 필요·로그인 확인 실패·기관/작업자 불일치·설정 변경·공용 점유 변경, 6-1 공용 업무데스크 탭 변경, 화면 읽기 응답이 끝나지 않은 경우(같은 화면을 쓰는 다음 대상도 진행할 수 없음)처럼 명시적인 공통 오류가 나오면 그 뒤 대상은 시작하지 않는다(미시도). 대상별 결과를 로컬에 기록하지 못하면 그 대상을 미확인으로 두고 멈춘다. 이전 실행의 실행 기록 잠금이 남은 대상은 시작하지 않고 미처리로 둔다. 이 순차 실행의 점유로 그 대상을 복구하지 않는다.
- 미확인 대상이 남으면 공용 점유가 유지되어 새 실행(같은 목록의 재실행 포함)이 막힌다. 미확인 대상마다 아래 진단 명령에 그 대상의 등록폴더를 주고 대조·복구한다. 순차 실행 결과의 `leaseId`를 `--release-lease`로 넘긴다. 순차 실행에서 시작하지 않은 대상이나 이미 처리된 대상에는 이 점유를 쓸 수 없다. 마지막 미확인 대상이 정리될 때 공용 점유가 풀린다. 복구 결과의 `leaseRetained`가 true이면 다른 미확인 대상이 남아 있다. 업무데스크의 미확인 대상은 검토완료 상태로 남고 등록완료로 바뀌지 않는다.
- 순차 실행 자체가 대상 사이에서 중단되어 결과가 없으면 `state/runtime.lock`의 `operation`(`evaluation-sequence:<실행 ID>`)과 `id`를 확인한다. 시작한 대상 중 실행 기록 잠금이 남은 대상을 먼저 위 진단 명령으로 정리한 뒤 `evaluation-sequence-release`로 공용 점유만 푼다. 이 명령은 소유 프로세스 종료와 같은 기관·설정을 확인하며 사이트에 쓰지 않는다.

## 제어 명령

현재 기관의 로컬 상태 폴더에 요청·명세·서식·정책·검토본·실행 기록을 둔다. 기관별 업무데스크 ID를 설정하고 현재 브라우저에서 관찰한 20L·20A·업무데스크 탭을 바인딩한다. 6-2만 진행할 때는 20L과 업무데스크가 필요하다. 기관별 연결용 비밀값은 첫 게시와 등록 사이에 유지한다. 실제 승인 문구 및 대상과 해시를 비공개 지시서에 기록한다. 최초 6-1 산출물은 출처를 다시 판단하기 위한 자료가 아니라 검토완료본의 대상과 무결성을 확인하기 위해 보존한다.

```text
node control.cjs evaluation-collect --request <요청.json> --out <새 수집폴더>
node control.cjs evaluation-prepare --spec <명세.json> --schema <서식.json> --bundle <근거.json> --policy <정책.json> --out <새 검토폴더>
node control.cjs evaluation-desk-publish --work <검토폴더> --instruction <게시 지시.json>
node control.cjs evaluation-desk-publish-sequence --tasks <작업목록.json>
node control.cjs evaluation-desk-publish-check --work <검토폴더> --instruction <게시 지시.json> --release-lease <점유 ID>
node control.cjs evaluation-desk-register-prepare --work <6-1 검토폴더> --instruction <등록 준비 지시.json> --out <새 등록폴더>
node control.cjs evaluation-desk-register --work <등록폴더/review> --instruction <등록 지시.json>
node control.cjs evaluation-desk-register-sequence --tasks <작업목록.json>
node control.cjs evaluation-sequence-release --sequence <실행 ID> --release-lease <점유 ID>
```

- 게시 지시에는 `action: evaluation-desk-publish`, `allowWrite: true`, `organizationId`, `deskOrgId`, `recipientName`, 실제 지시 `message`와 `specHash`, `schemaHash`, `bundleHash`, `policyHash`를 넣는다.
- 등록 준비 지시에는 `action: evaluation-desk-register-prepare`, `organizationId`, `deskOrgId`, `message`와 대상이 특정된 경우 `evaluationKey`를 넣는다. 등록 지시는 `action: evaluation-desk-register`, `saveAllowed: true`, 기관 ID와 `message` 및 `prepared.json`의 `evaluationKey`, `contentHash`, `actualRound`, `originalBundleHash`, `documentSha256`를 사용한다.
- 순차 작업 목록은 `{"schemaVersion":1,"phase":"6-2","tasks":[{"taskId":"<불투명 로컬 ID>","instruction":"<단건 등록 지시.json>","work":"<등록폴더/review>"}]}`이다. 6-1 게시 목록은 `phase`를 `6-1`로 하고 `instruction`에 게시 지시, `work`에 검토폴더를 넣는다. 명령과 목록의 단계가 다르면 실행하지 않는다. taskId는 영문·숫자·`_`·`-`만 쓰고(대소문자만 다른 ID는 중복) 이름·인정번호를 쓰지 않는다. 결과는 `processedIds·manualIds·unknownIds·notAttemptedIds·stopped·stopReason`으로 돌려주고, 대상별 기록은 상태 폴더 `skills/longterm-result-evaluation/sequences/<실행 ID>`에 남는다. unknownIds가 있으면 전체 성공이 아니다.
- 완료 확인에 실패하면 결과에 따라 `evaluation-collection-check`, `evaluation-desk-publish-check`, `evaluation-desk-claim-check`, `evaluation-desk-read-check`, `evaluation-read-check`, `evaluation-reconcile`, `evaluation-desk-report`로 같은 실행을 진단한다. 새 실행으로 우회하지 않는다.

여기서 자동 진행은 지정된 업무를 실행하는 동안의 순서를 뜻한다. 업무데스크의 상태 변화를 상시 감지하는 기능은 연결되어 있지 않다.


## 6-2 시작 화면과 반복 평가 검사

로그인과 탭만으로 대상 화면이 준비됐다고 가정하지 않는다. 현재 기관/20L/종사자와 미저장 편집을 먼저 읽고, 사용자가 업무창을 닫았다면 정상 메뉴의 결과평가를 열어 정확한 수급자·계획을 선택한 뒤 등록 준비를 시작한다. 6-2에는 RFID/업무수행일지 재수집이 필요 없다. 이미 작성된 다른 초안을 자동 초기화하지 않는다.

서비스기간의 시작일·종료일 차이 또는 겹침은 반복 평가의 중복 기준이 아니다. 승인된 전체 계획기간을 보존하고 별도의 평가일·차수·대상/계획·기존 저장/unknown 이력을 검증한다. 동일 평가일 중복 및 잘못된 차수는 계속 차단한다.
