# 계획서 내용과 현재 기관 정책

이 문서는 기관이 검토할 작성 기준이다. 제작자의 실제 계획서·개인 사례·문장 코퍼스는 배포하지 않는다.1~5등급의 시간·서비스·동의·기간은 현재 기관의 채택 기준, 해당 대상의 실제 평가/계약과 확인된 요구를 대조한다. 코드가 등급만으로 시간/서비스를 늘리거나 부축을 자동 추가하지 않는다.

## 근거와 문장

욕구사정의 실제 체크·메모를 중심으로 최근 낙상·욕창·인지 자료와 날짜·작성자·서식·판정을 함께 읽는다. 총점만 보고 검사 생략/치매약 복용·인지 정상·위험 판정을 만들어 쓰지 않는다. 빈 항목은 정상/없음/자립으로 바꾸지 않는다. 기존 계획·새평가·사용자 설명이 충돌하면 원문과 확인 필요 사항을 개인 근거에 남긴다.

이용계획서에 있는 필요내용을 욕구/기능 근거 없이 전부 추가하지 않는다. 이동·위생·식사·배설 등 실제 도움 단계와 서비스의 근거를 연결한다. 부분 기록으로 생활 전반 자립을 주장하지 않는다. 이전 초안의 서비스/문구가 이번 대상에게 자동 적용되지 않는다.

목표·종합의견은 짧은 기록체로 작성한다. 같은 사실을 반복하지 않으며 검토 과정/근거 부족 설명은 임상 본문 밖의 확인사항에 둔다. 구성은 이용자 상태·필요성, 제공 서비스/목표, 이용계획서와 다른 부분, 위험 평가 반영, 제공방법/자원 등을 사용할 수 있다. 소제목/문장 구성은 기관에서 정하며 빈 영역을 채우기 위해 사실을 만들지 않는다.

## 명세에 필요한 실제 값

- 확인한 계약 방문시간과 종합의견 제공시간이 등급 자동 180/240분보다 최우선이다. 계약·종합의견·일 단위 항목 합계가 같아야 하며 범위·대략·미확인 표기는 확정하지 않는다. 필요한 양치 10분을 짧은 계약이라는 이유로 필요시로 내리지 않는다. 기관이 채택한 양치·취사·청소 고정 항목만으로 시간을 초과해도 임의 삭제/축소하지 않고 미해결로 남긴다. 실제 필요서비스와 다른 기관의 개인 사례를 자동 복사하지 않는다.
-5등급 인지활동형의 서비스와 두 활동의 배분은 해당 대상의 현재 근거로 정한다. 화면상 하나의B30항목이면 같은 필요내용을 중복 선택하지 않고 총분/세부목표를 실제 서식에 맞춰 확인한다. 등급만으로 검사 결과·분배·도움 제공을 추정하지 않는다.
- 적용 시작·종료·작성일·재작성 사유와 인정순번/이용계획서순번을 현재 원문에서 확인한다. 계약 종료 후 재진입을 자동 최초계약으로 분류하거나1년·101/001을 자동 대입하지 않는다. 이용계획서 번호가 불명확하면 입력용spec을 보류한다.
- 새 계획서 레코드를 등록한다는 이유로 최초 계약으로 분류하지 않는다. periodBasis.type은 initial(신규 최초 제공), continuation(이전 계획 종료 다음 날), renewal(갱신 인정 시작일)로 구분하며 실제 계약·인정기간을 함께 기록한다. 작성일과 적용 시작일은 각각 보존한다. continuation에는 이전 계획 번호·종료일이 필요하다. newContract는 initial에서만 true이며 갱신은 false다.
- 같은 기간에 계획서가 있다는 사실은 새 작성 금지의 충분한 이유가 아니다. 사용자의 기존본 보존·추가 작성 지시는 creationIntent의 고유 요청ID·원문·시각·현재 겹치는 보존 대상 번호와 evidence.creationIntent로 연결한다. 같은 요청은 새 해시로 다시 등록하지 않고 새 요청과 실수 재시도를 구분한다. 적용기간을 억지로 변경하거나 기존본을 삭제·수정하여 새 작성을 대신하지 않는다.
- 이용계획서 비교는 실제 차이 내용 또는 사용자 확인의 NONE/SKIP 결정으로 기록한다. NONE/SKIP은 모델이 누락을 숨기는 기본값이 아니다.
- 동의방법/관계·동의자·실제 동의일·전화·최종확인자는 이번 대상의 자료나 실제 사용자 보완 사실로 확인한다. 현재 저장 실행기는 직접동의/본인 방식만 지원하므로 다른 방식은 지원을 확인하기 전 입력하지 않는다. TODAY·본인동의·가상번호·작성자=확인자를 자동 생성하지 않는다.

## 근거 연결 내용 파일

`schemaVersion:1`, `orgName`, 원천 파일의 정확한 `sourceSha256`, 실제 newContract 범위, visits(필요 시), `differenceDecision`, `spec`, `evidence`를 갖는다. `spec`의 목표·종합의견·선택 항목·세부목표는 Codex가 원천을 읽어 판단해 작성한다. 생성기는 문장을 추론하지 않고 식별·형식·근거 연결·누락을 검사해 문서로 만든다.

`spec`은 현재 version2이며 name/grade/ltcMgmtNo/planNo/adptFr/adptTo/writeDate/contractEnd/visits/reason/items/subGoals/goal/opinion/agree/writer/writerJob/confirmer/decisionNeeded와 미해결·근거를 갖는다. items는 이름·FTU·payType·cycle/count/minutes를 명시하며 필요시는 count0, 일은 실제 횟수를 쓴다. 정적 필요내용 정의는 현재 버전 `assets/static/lt-need-catalog.json`이다. 코드표의 빈 목표/세부문장을 제작자의 과거 문장으로 채우지 않는다. 현재 생성기의 쓰기 전 검사를 통과한 경우에만 입력 spec을 만든다.

evidence는 goal/opinion, `item:<필요내용 이름>`, `subGoal:<FTU>`, agree/confirmer와 visits/contractEnd/differenceDecision에 연결한다. source 근거는 실제 원천 JSON pointer, user 근거는 실제 발언과 출처를 갖는다. 예를 들어 source는 `kind:source,pointer:/r/out/0/assess/0/rows`, user는 `kind:user,source:<발언 식별>,message:<실제 발언>`이다. 포인터가 존재한다는 사실은 문장 의미의 타당성까지 증명하지 않으므로 임상 판단과 사용자 검토를 생략하지 않는다.

개별 facts/동의/순번/날짜/세부목표가 미완료이면 DOCX의 입력 전 확인에 남기고 입력용spec은 만들지 않는다. 내용을 보완하면 같은 원천과 새 내용 파일로 새 폴더에 생성한다. 기존 문서/명세/시도 이력을 지우거나 덮어쓰지 않는다.
